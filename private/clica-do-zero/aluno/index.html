Método PAV: a regra que evitou quebrar o que já funcionava

P — Pedir exatamente

Antes de qualquer alteração, descreva o resultado desejado e também o que não pode ser mexido. Em projetos reais, dizer apenas “melhore” abre espaço para mudanças desnecessárias.

A — Alterar só o necessário

Uma correção pequena deve continuar pequena. Se o problema está na imagem do carrinho, não é motivo para reconstruir o cabeçalho inteiro.

V — Validar antes de continuar

Não confie apenas no código. Depois da alteração, valide a versão publicada, navegue pelo fluxo e confirme que o que estava funcionando continua funcionando.

Prompt pronto
Altere somente [ELEMENTO]. Preserve todo o restante exatamente como está. Não remova funcionalidades existentes. Depois da alteração, valide a versão publicada e me informe apenas o que foi alterado e o resultado da validação.
Prompt de diagnóstico antes de mexer

Um dos padrões mais úteis foi separar diagnóstico de execução. Primeiro entender, depois alterar. Isso reduz correções em cascata.

Prompt pronto
Analise o problema sem alterar nada primeiro. Identifique a causa provável, o arquivo ou componente envolvido e o menor ajuste necessário. Só depois aplique a correção, sem mexer em outras partes.

Quando usar

  • Imagem fora do enquadramento.
  • Botão que parou de responder.
  • Carrossel que mostra só um banner.
  • Link que abre página errada.
  • Deploy que conclui mas a versão publicada parece antiga.
GitHub + Railway: publicar sem fingir que deu certo

O fluxo confiável foi: editar no repositório, gerar commit, aguardar o deploy e só então validar a URL pública. “Código enviado” não é igual a “site publicado”.

GitHub → commit na main Railway → build/deploy Status esperado → SUCCESS Depois → abrir URL pública e validar a mudança

Lição que vale para qualquer projeto

Nunca declarar uma correção concluída antes do ambiente publicado confirmar. Várias falhas apareceram somente depois do deploy.

Erros reais que viraram ensinamento
  • Arquivo com nome duplicado, como logo.png.png, pode parecer correto visualmente no computador e falhar no site.
  • Um produto disponível ontem pode ficar indisponível hoje; preço, link e disponibilidade precisam ser conferidos.
  • Links de busca não devem substituir links de produto quando a intenção é vender um item específico.
  • Carrossel com quatro arquivos não significa carrossel funcionando; precisa existir lógica de navegação e todos os slides precisam ser carregados.
  • Em Express moderno, rotas genéricas mal configuradas podem gerar erro de path-to-regexp.
  • Um zoom bonito pode continuar ruim se não ampliar exatamente a região sob o mouse.
Vitrine que vende: o que aprendemos nos cards

Um card não é só imagem + preço. O comprador precisa reconhecer produto, loja, confiança e próximo passo rapidamente.

  • Imagem real e bem enquadrada.
  • Nome legível e específico.
  • Preço real quando disponível.
  • Avaliação e quantidade de avaliações quando a origem fornece esses dados.
  • Categoria curta e intuitiva.
  • Loja de origem identificável sem poluir o visual.
  • CTA claro, como “Comprar agora”.
Prompt pronto
Padronize este card sem alterar os demais. Mantenha imagem, nome, preço e link reais. Corrija somente hierarquia visual, enquadramento e consistência com os cards existentes.
Produtos de afiliado: disciplina antes de publicar

O erro mais caro em afiliados é publicar informação bonita porém errada. Antes de adicionar um item, valide quatro coisas: disponibilidade, foto, preço e destino do link.

Checklist do produto [ ] Produto específico [ ] Disponível [ ] Foto corresponde ao item [ ] Preço atual [ ] Link afiliado correto [ ] Loja identificada [ ] Página de destino abre o item esperado

Quando um produto deixa de existir, a solução não é improvisar um substituto visualmente parecido; é procurar outro item real e refazer os dados.

Página de produto: confiança antes do clique

A página precisa responder rapidamente: o que é, para quem serve, por que vale a pena e onde comprar. Fotos adicionais ajudam, mas precisam representar o mesmo produto.

Aprendizado do zoom

O zoom só ficou realmente útil quando passou a acompanhar a posição precisa do cursor. “Aumentar a imagem” e “ampliar exatamente onde o usuário aponta” são problemas diferentes.

Prompt pronto
Melhore somente o zoom da imagem principal. A ampliação deve acompanhar com precisão a posição do mouse, sem alterar layout, fotos, botões, preço ou conteúdo da página.
SEO do zero: publicar não basta

O projeto só começou a ficar preparado para tráfego orgânico quando página, metadados, sitemap, robots e Search Console passaram a fazer parte do processo.

  • Título e descrição precisam representar a página de verdade.
  • URLs devem ser estáveis e fáceis de entender.
  • Indexação precisa ser conferida, não presumida.
  • Conteúdo útil deve apontar para páginas que realmente ajudam o usuário.
Publicar → conferir URL → sitemap/robots → Search Console → aguardar indexação → medir impressões e cliques → melhorar
Métricas: clique é uma pergunta respondida pelo usuário

O objetivo não é colecionar números. É descobrir quais produtos, seções e chamadas despertam interesse suficiente para levar a pessoa ao próximo passo.

Perguntas práticas

  • Qual produto recebe mais cliques?
  • Qual seção gera mais saída para Amazon, Shopee ou outra loja?
  • Qual criativo traz visitas que realmente navegam?
  • O usuário chega ao botão de compra?
Prompt pronto
Não me mostre apenas visitas. Separe o comportamento por produto, seção e origem do clique. Quero descobrir onde existe intenção real e qual próximo teste faz sentido.
Conteúdo, Reels e anúncios: atenção precisa ter destino

Memes, vídeos curtos e criativos podem gerar atenção, mas precisam levar a uma oferta ou produto claro. O conteúdo não pode terminar no próprio conteúdo.

  • Mostrar o produto cedo.
  • Vídeos curtos, objetivos e reutilizáveis.
  • Alternar conteúdo divertido e conteúdo de produto.
  • Usar CTA coerente com a página de destino.
  • Começar com orçamento controlado e aprender antes de escalar.
Exemplo de comando
Crie um criativo vertical de 15 segundos. Mostre o problema nos primeiros segundos, apresente o produto em uso, destaque um benefício real e termine com um CTA simples. Sem promessas exageradas.
Funil do Clica do Zero: menos etapas, mais clareza

O fluxo foi organizado para não misturar captura, prévia e venda em uma única página.

Página do curso → Prévia gratuita → Captura de nome + e-mail → Prévia liberada → Oferta completa → Checkout Hotmart

Klaviyo ficou responsável por captura e comunicação. Hotmart ficou responsável pelo pagamento. O site ficou responsável pela experiência, conteúdo e ligação entre as etapas.

Webhook e área do aluno: segurança de verdade

Esconder uma URL não protege um curso. A área só passou a fazer sentido quando o acesso foi validado no servidor.

Compra aprovada → Hotmart envia Webhook V2 → Railway valida autenticação → Supabase registra aluno ativo → login consulta status → conteúdo é entregue somente se o acesso estiver ativo

Também validamos o caminho inverso: um acesso revogado deixou de entrar mesmo após já ter funcionado antes.

Regra de segurança

Tokens, chaves e segredos nunca devem aparecer no HTML, em prompts para alunos ou no repositório público. Exemplos do curso usam sempre placeholders.

Prompt para integrações sem destruir configurações existentes
Prompt pronto
Na ferramenta já aberta, altere somente [CAMPO/INTEGRAÇÃO]. Preserve nome, produto, preço, checkout, conteúdo e todas as configurações existentes. Não regenere tokens. Não faça ações pagas. Antes de salvar algo sensível, pare e mostre exatamente o que será alterado.

Esse padrão foi especialmente importante em Hotmart, automações, anúncios e integrações externas.

Prompt para corrigir sem reconstruir
Prompt pronto
Corrija somente o problema descrito. Não refatore o projeto inteiro, não troque estilos que já funcionam e não remova elementos existentes. Se houver mais de uma solução, prefira a menor alteração possível e valide depois.

Essa orientação parece simples, mas virou uma das maiores economias de tempo do projeto.

Prompt para transformar experiência em curso

O Clica do Zero nasceu da prática: primeiro veio o projeto, depois a organização do método. Isso evita um curso feito apenas de teoria.

Prompt pronto
Transforme este aprendizado real em uma aula prática. Explique o problema, a tentativa inicial, o erro encontrado, a solução que funcionou, o princípio geral que o aluno pode reutilizar e um exercício para aplicar no próprio projeto.
Checklist mestre antes de publicar qualquer mudança
[ ] Mudança corresponde exatamente ao pedido [ ] Nada fora do escopo foi alterado [ ] Links continuam funcionando [ ] Imagens carregam corretamente [ ] Mobile continua utilizável [ ] Dados reais não foram substituídos por placeholders [ ] Build/deploy terminou [ ] Versão publicada foi conferida [ ] Próxima alteração só começa depois da validação
O princípio central do projeto

IA não substitui direção. Ela acelera pesquisa, criação, código, conteúdo, análise e operação. Mas o resultado melhora quando existe uma pessoa definindo limites, verificando fatos e decidindo o que não deve ser alterado.

O objetivo do Clica do Zero não é ensinar a “pedir qualquer coisa para a IA”. É ensinar a transformar intenção em projeto real, com checkpoints, validação e aprendizado acumulado.

Liberdade para criar

Você não está aprendendo a criar apenas uma loja.

Os princípios do Clica do Zero servem para criar praticamente qualquer projeto ou site que seja permitido na internet. O formato pode mudar completamente, mas a lógica de ideia, estrutura, experiência, publicação, validação e melhoria continua a mesma.

Prompt para transformar uma ideia em qualquer projeto de site
Prompt pronto
Quero transformar a ideia [DESCREVA A IDEIA] em um projeto real na internet. Primeiro defina objetivo, público, ação principal do usuário, páginas essenciais, conteúdo necessário, funcionalidades mínimas e riscos que precisam ser validados. Depois proponha uma experiência que desperte curiosidade, criatividade e vontade de explorar, sem perder simplicidade na primeira versão. Por fim, monte uma estrutura de MVP que eu consiga publicar, testar e melhorar.

O que esse prompt ensina

Você deixa de pedir “faça um site” e passa a construir com intenção: problema, público, fluxo, escopo, risco, publicação e validação.

Laboratório de criatividade

Desafio de curiosidade

E se existisse uma rede social só para aprender fazendo?

Imagine perfis baseados em projetos reais, feed de progresso, desafios semanais e pessoas acompanhando a evolução umas das outras. O exercício é pensar no que faria alguém voltar amanhã.
